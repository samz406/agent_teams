# Agent Teams 数字员工场景能力差距分析

> 评估基线：`samz406/agent_teams` main，commit `bb211bf`。本文对照“长期岗位制数字员工”场景，判断当前 Agent Teams 已经具备什么、缺少什么，以及产品下一阶段应该向哪里演进。

## 1. 结论

当前 Agent Teams 已经具备数字员工团队的执行骨架，但还没有完整成为“长期岗位制数字员工平台”。它现在更准确的定位是：**围绕一次 Change 和 Workspace 组织真实 CLI Agent，通过 Workflow、Handoff、Evidence 和人工 Gate 完成可验证的软件研发工作。** 如果按长期数字员工的完整场景评估，底层能力大约具备 50%～60%；如果只评估代码开发、测试、审查和交付，则完成度明显更高。

两类产品的核心组织单位不同。Grok Bot 一类产品从“岗位”出发，关注这个数字员工长期负责什么、何时自动工作、积累了什么经验、能调用哪些业务工具；Agent Teams 当前从“变更”出发，关注这次 Change 包含哪些 Task、在哪个 Workspace 执行、如何交接以及用什么 Evidence 验收。

```text
当前 Agent Teams：Change → Workflow → Task → AgentSession → Run → Evidence
长期数字员工：Agent 岗位 → Memory / Skill → WorkOrder → Run → Handoff → 经验沉淀
```

因此，当前 Agent 是“长期存在的责任角色”，但还不是“越工作越熟悉组织要求、能够周期性自主交付结果的数字员工”。

## 2. 能力对照

| 能力 | 当前状态 | 代码层面的实际含义 |
|---|---|---|
| 有名字、职位和岗位说明 | 已实现 | `Agent` 已保存名称、描述、责任边界、质量标准、Runtime、Workspace Scope 和默认权限，并提供创建、编辑页面 |
| 长期负责一类结果 | 部分实现 | 岗位身份长期存在，但还没有长期结果、固定数据源、标准交付物、失败策略、人工审批点等完整岗位模型 |
| 单项工作上下文续接 | 已实现 | `AgentSession` 保存原生 CLI Session ID；同一 Change、Agent、Workspace 内可 Resume |
| 跨任务长期记忆 | 未完整实现 | `AgentSession` 唯一范围是 `Change + Agent + Workspace`；新 Change 会建立新 Session，不会自动继承该 Agent 以前任务中的纠正和经验 |
| 多 Agent 任务交接 | 已实现 | `team-actions` 可以产生结构化 Task、Handoff 和真实子 Run，且目标 Agent 必须属于当前团队 |
| 多人讨论 | 已实现 | 支持 2～6 个角色、独立 Session、共享上下文、Leader 收敛、@角色、暂停恢复、Markdown 产物和转正式任务 |
| Skill 工作方法沉淀 | 未实现 | 没有 Skill、SkillVersion、测试记录、启用范围和运行时调用机制 |
| 定时任务 | 未实现 | 当前 Scheduler 是 Workflow 阶段调度，不是按时间触发的 Cron/周期任务 |
| 关闭窗口后继续运行 | 未实现 | Runtime 是 Electron Utility Process；应用退出后活动 Run 会中断，重启时被恢复为 `INTERRUPTED/BLOCKED` |
| 云电脑 | 未实现 | 当前使用本机 CLI、本机 Workspace 和 Git Worktree，没有托管 Linux 云桌面 |
| 业务连接器 | 未实现 | 可以使用底层 CLI 已有工具和网络能力，但没有统一 OAuth 连接器、凭据管理、能力声明和插件市场 |
| 权限与人工审批 | 部分实现且研发场景较强 | 已有 Agent-Workspace 权限硬校验、Git Worktree、Artifact Gate 和 HumanIntervention；缺少发送、发布、付款、删除等业务动作级审批策略 |
| 可验证交付 | 已实现且是核心优势 | Run、命令、Git、Diff、测试、Evidence、Blocking Issue 和独立 QA 构成了比普通聊天式 Agent 更严格的验收链路 |

## 3. 已经可以稳定支撑的场景

### 3.1 软件研发数字员工

让 Code Agent 长期负责某个代码仓库的开发、测试和修复，Architect 负责边界审查，QA Agent 负责独立验证，Leader 负责分工与 Evidence 验收，这类场景已经与当前架构高度匹配。Agent Teams 在 Git Worktree 隔离、权限硬校验、真实 CLI、Session Resume、Diff/Test Evidence 和独立 QA 方面，甚至比通用数字员工产品更严格。

### 3.2 一次性的多 Agent 研究或讨论

用户可以创建圆桌、头脑风暴、正反辩论、专家会诊、务虚会和六顶思考帽讨论。每个讨论角色拥有自己的 Session，能够接收共享上下文并由 Leader 收敛结果。讨论产物可以导出，也可以转换为正式 Change。这适合一次性的方案研讨，但不等于某个岗位长期自动积累知识并定时交付。

## 4. 目前无法完整支撑的场景

### 4.1 情报总监每天自动提交晨报

当前可以手动创建调研任务，让 Agent 使用本机 CLI、网络和文件完成研究；但没有经过验证的 Skill、周期计划、后台常驻调度、连接器和跨 WorkOrder 岗位记忆，所以无法稳定做到“每天自动运行、核验来源、失败告警、避免重复发送、关闭窗口后继续执行”。

### 4.2 电商数字员工团队

当前可以把脱敏 CSV 放入 Workspace，由库存分析员、内容专员和售后助理分别分析，再通过 Handoff 交给 Leader 汇总。但系统还不能直接管理店铺、表格、邮箱等连接器，也没有改价、退款、发消息等动作级审批规则，因此只能形成半自动分析链路，不能成为稳定的业务运营系统。

## 5. 最关键的架构判断

长期数字员工不应该永久复用一个不断膨胀的原生 Session。永久 Session 虽然短期看似节省重复输入，但会带来上下文污染、窗口耗尽、缓存失效、无关历史干扰和 Token 成本持续增加。正确方案是：**岗位身份和长期记忆持续存在，每个 WorkOrder 使用独立 Session；执行前只检索并注入与本次工作相关的记忆，同一 WorkOrder 内再使用 Native Session Resume。**

建议形成四层长期记忆：

1. `RoleMemory`：岗位职责、用户偏好、质量规则、禁止动作和审批边界。
2. `ProjectMemory`：某个 Workspace、客户或业务项目的长期事实和关键决策。
3. `EpisodeMemory`：历史 WorkOrder 的目标、结果、失败、人工纠正和复盘摘要。
4. `WorkflowMemory`：跨角色协作顺序、交接规则、常见阻塞和改进建议。

Skill 保存“这类工作怎样稳定完成”，WorkOrder 表达“这一次具体要完成什么”，Schedule 决定“什么时候创建并启动下一张 WorkOrder”。三者不能混在 Agent 岗位说明或同一个聊天 Session 中。

## 6. 产品演进方向

下一阶段建议分两组推进：

**第一组：长期岗位模型 + 分层记忆 + Skill。** 让 Agent 从静态角色升级为具备长期结果、固定标准、可审计记忆和可版本化工作方法的数字员工；人工纠正先形成 Memory Candidate，经确认后再成为长期规则，避免模型把错误结论写入永久记忆。

**第二组：WorkOrder + 定时任务。** 把通用工作从研发 Change 中独立出来，支持人工、Schedule 或 Agent 创建 WorkOrder；通过幂等键、并发策略、时区、错过执行策略和后台 Runtime 保证周期任务不会重复、漏跑或静默失败。
